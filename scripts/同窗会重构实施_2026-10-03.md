## 一、第一性原理逐条推演

### 1. 为什么「配对」和「对话」必须拆开？

骚扰发生在**对话里**，不在配对里。
把两者拆开，才能在危险发生**之前**插一道门。

摇一摇的问题是：摇到即开聊，门开在危险**之后**——人已经进来了。

**推论**：配对阶段**不需要消息体系**。配对只是信息交换 → 不需要房间、不需要聊天记录、
不需要 participants。所以 `pairing.ts` 完全不依赖 `messageStore`，房间只在配对**成功之后**才出现。

### 2. 为什么不能做「隐私开关」？

若隐私做成全局开关，会触发反向激励：
多数人保守 → 匹配率暴跌 → 少数人全解锁 → 保护机制崩溃。

**所以保护必须是默认态**：不设 ≠ 设为公开，而是**不设就等于有保护**。
实现为产品固定分层（L0/L1/L2）+ **每次配对决定走不走**。

### 3. 为什么跳过必须「不写记录」？

跳过落库 = 对方可查 = 被跳过从「不可见」变「可见」。
这道门就从**后面**被撬开了。

**所以**：跳过不写任何记录（默认行为，反而更省代码），只写本地 `skipSet`。
用户认可：拒绝是可见的、跳过是不可见的；拒绝可能招致报复，跳过不会。

### 4. 为什么配对成功要「不排他」？

排他 = 一对一 = 你等我我等你 = 约会软件。
用户做的是「同好连接」，产品是三底线之一「不做社交 feed」。
**不排他 = 可以同时认识几个人 = 漫展扩列**。

天然限流：时间窗 + 同时在场同时在找，不会变成公共目录。

### 5. 为什么产物要「当场有效」？

配对的产物是「我知道此刻有这个人」，**过了此刻就没有意义了**。
留下反而累积成负担——用户原话：「漫展扩列常变成列表尸体，不需要这种关系」。

### 6. 双重确认的两道门，问的必须是不同的事

- 第一道：我愿意让**这个人**看到我（关于人 / 交换信息）
- 第二道：我愿意**现在**开始说话（关于此刻 / 投入时间）

若两道门都问「你愿不愿意和这个人交流」，第二道就是废话。

### 7. 【测试发现】算法不能当门卫

原实现 `pickBestMatch` 用 `score > 0` 过滤候选。
小池子里无交集是**常态** → 频繁返回 null → 用户看到「没人」。

**最致命处**：用户分不清「池里真没人」和「有但被算法滤掉了」，两者长得一样。

**修正**：推开窗这个动作**本身就是信号**。「此刻我们都在这里」已是一条真实连接，
不需要算法背书。**分数只用于排序，不该用于许可。**

### 8. 【配套】小池子 × 双向不可见过滤 → 必须显示池子规模

左滑式不可见过滤成立的前提是**池子够大**（约会 app 百万级）。
P0 是**一场漫展几十人**，双向不可见 × 小池子 → 可能一次都匹配不上，
且**双方都不知道为何**。

于是会出现：「越保护 → 越容易零匹配 → 用户以为这产品没人用 → 走掉」，
**保护机制本身会把用户赶走**。

**解法**：显示**聚合规模**（只给总数，不给是谁）。
- 不泄露任何个体，不破坏「被跳过不可见」
- 把「黑等」变成「可行动的等」
- 池子为 0 时也诚实：那是真的没人，不是你的问题

## 三、Bug 修复：联网也显示感叹号

**根因**：`radar_room_messages` **无 `status` 列**（三个迁移都没建），
但 v0.9.23.4 把 `status: 'sending'` 一起 insert → PGRST204 → insErr → 标 failed → 感叹号。

**结论**：**只要发消息就必然失败，与联网无关。**

**修法**：剥离而非加列。`status` 是本地瞬时 UI 状态，落库有三重害处（见源码注释）。
