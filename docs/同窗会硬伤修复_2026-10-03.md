## 修复清单

### ① `onlineCount` 硬编码 `ref(1)` → 解散弹窗是死代码

**原缺陷**：`const onlineCount = ref(1)`，全项目仅声明处赋值，从未被订阅或更新。
连带：`otherCount = onlineCount - 1` **恒为 0** → 解散确认弹窗（v0.9.23.3 专门做的 MUJI 双按钮）**永不触发**；顶部「N 人在线」是假数据。

**改法**（`RadarRoomView.vue`）：
- 改为 `participantCount = computed(() => 1 + (room.value.participants?.length || 0))`
- 解散判断改为直接读 `room.value.participants?.length`
- **命名从 `onlineCount` 改为 `participantCount`**：它数的是「进入过房间的人数」，不是实时在线数（P0 无 presence 订阅）。保留 `onlineCount` 这个名字本身就是个小谎言。
- 显示文案「N人在线」→「N人参与」

**未做**：真正的实时在线数需要 Supabase Realtime Presence，属重构范畴。

### ② `/radar` 路由不存在 → 8 处跳转白屏

**原缺陷**：`router/index.ts` 里**从未定义 `/radar`**（只有 `/radar/launch`、`/radar/room/:id`、`/radar/:expoId`）。但 8 处代码 `push('/radar')`。其中两处是**登录后落点**。

**影响面**（实测）：
| 位置 | 后果 |
|---|---|
| `SelectView.vue` L20 | 已登录用户进入 App → **白屏** |
| `LoginView.vue` L25 | 登录成功 → **白屏** |
| `RadarRoomView.vue` ×5 | 「←」返回 / 解散后 / 退出后 / 房间不存在 → 白屏 |
| `RadarLaunchView.vue` L30 | 未登录 → 白屏（此路径不可达，因 `/radar/launch` 不在 NEED_AUTH，属死分支） |

**改法**：同窗会列表 section 在**首页**（v0.9.20 quickTab 重构后从独立页移入），故统一改为 `/home#section-radar`
- 7 处改 `/home`（登录/已登录落点 → `/home`；房间页返回/解散/退出 → `/home#section-radar`）
- `RadarLaunchView` 的不可达死分支顺手修为 `/home`

**注**：`/home` 在 NEED_AUTH 内，未登录访问会被守卫重定向；`LoginView` 登录成功后 session 已建立，不会被弹回。

### ③ 「在场确认」文案是虚假承诺

**我最初的判断错了，在此更正**：我先说「从没实现过」，不准确。

**真相**：`matching-v3.ts` 的 `sceneScoreV3()` **逻辑是写了的**——「同日期+同时段 → 30 分」、「同日期 → 22 分」，完整实现。但它的入口 `searchRadarV3()` **被导出、全项目零调用者**。另外 `searchRadarRooms()`（房间排序，真正在用的那个）**只算 interest/intent/area/identity，完全没有在场逻辑**。

即：**逻辑写完了，但从没接上线**；且代码满分是 **30**，文案写的是 **50**。

**改法**（`ExpoDetailView.vue`）：删除该句，附注释说明。待重构把漫展绑定接通后，再用真实文案恢复。

### ④ 房主解散后房间可能永久残留（隐私问题）

**原缺陷**：Q1 隐私修复靠 `setTimeout(..., 60_000)` 物理删除。用户切后台/杀进程时定时器不执行 → 房间与消息**永久残留**，恰好违背该修复的本意（用户明确要求临时聊天数据彻底删除、不留历史）。

**改法**（`radarStore.ts` 重写）：
- 新增 `purgeStaleRooms()` **惰性兜底清理**：每次 `fetchRadarRooms()` 后，回收「active 且已过期」或「closed 且过宽限期」的房间
- `closeRadarRoom`（房主）先标记 `status='closed'` + `closed_at`，再 `setTimeout` 即时删
- 双保险：定时器执行 → 立即回收；定时器未执行 → 下次有人打开 App 时兜底回收
- 判断逻辑抽为纯函数 `isPurgeable(r, nowMs)`，`closed_at` 缺失的老数据视为可删

### ⑤ `participants` 数组只增不减

**原缺陷**：参与者退出（`closeRadarRoom` 非 initiator 分支）只 `console.log`，**不从 participants 摘除**；`addSelfAsParticipant` 失败也不回滚。

**改法**：
- 新增 `removeParticipant(roomId, uid)`：本地摘除 + 同步远程
- `closeRadarRoom(roomId, false, uid)` 现在真正摘除
- `RadarRoomView.confirmLeave()` / `leaveRoom()` 传入 `currentUser.id`

---

### ⑥ 房间密码明文存库

**原缺陷**：`password?: string | null  // 明文存（P0 演示用）` → 存 Supabase。任何能 SELECT `radar_rooms` 的人可读所有房间密码；用户复用同一 PIN 时一处泄露等于多处泄露。

**改法**：
- 新增 `src/lib/roomPassword.ts`：`hashRoomPassword()` / `verifyRoomPassword()` / `isValidRoomPassword()`
- 存储 SHA-256（加 `kizuna-room:` 盐前缀）；Web Crypto 不可用时降级 FNV-1a（弱，仅避免功能不可用）
- 发起时存哈希，进入时哈希输入后比对
- 注释说明**兼容性**：早期明文房间无法通过校验（房间短时临时 + 会被 purgeStaleRooms 回收，影响可忽略）

**⚠️ 未解决（已如实标注）**：这**不是真正的访问控制**。哈希随房间数据下发到所有客户端，而 4-6 位纯数字搜索空间仅 10^4~10^6，可瞬间穷举。真正安全需**服务端校验**（Supabase RPC security definer，密码不出服务端）——需手跑 SQL，列为 P1。

## 实施明细

### ① 意图优先权重（`matching-v3.ts`）

`searchRadarRooms` 按房间是否填意图分流：

```
房间填了意图 → intent 0.45 + interest 0.35 + area 0.10 + identity 0.10
房间没填意图 → interest 0.45 + intent 0.25 + area 0.15 + identity 0.15（原行为）
```

依据：兴趣是不易改动的**长期项**，意图是**临时项**；「我想要什么」是本次匹配的关键项。

### ② 漫展绑定 + 同场加分（`matching-v3.ts` / `mockData.ts` / `RadarLaunchView.vue`）

- `RadarRoom` 新增 `expo_id?: string | null`
- 新增 `computeExpoBonus()`，分级取最高一档：

| 分 | 条件 | 文案 |
|---|---|---|
| 30 | 同场 + 同日 + 同时段 | `{漫展} {时段}同在` |
| 22 | 同场 + 同日 | `{漫展} 同日` |
| 15 | 只有「我」在这一场（读不到对方 presence 时的兵底） | `你也在这场` |
| 0 | 未绑漫展 / 我不在场 | — |

- 发起页线下模式加漫展 chip 选择（**选填**，仅列 `ongoing`/`upcoming`）
- 总分 `min(100, base + expoBonus)`

### ③ presence 数据源（`venue.ts`）

**新发现的问题**：`venue_presence` 的 `loadMyPresences` **只加载自己**的记录，没有读全体数据的能力 → 同场加分在真实数据下永远拿不到 22/30 分。

**改法**：新增 `fetchAllPresences()`（best-effort）+ `allPresences` computed；HomeView 在 `onMounted` 调用。读不到（RLS 限制）→ 静默降级为空数组 → 自然退回旧行为，不阻断页面。

**⚠️ 隐私代价（已写入 SQL 注释）**：放开 `venue_presence` 读权限等于让任何登录用户读到「谁在哪场漫展、哪个时段」。需用户自行判断是否接受，SQL 中默认注释掉。

### ④ 迁移未执行时的优雅降级（`RadarLaunchView.vue`）

**发现的部署风险**：若 `expo_id` 列未创建，`insert` 会**整体失败** → 房间只能存本地，用户看到假的「网络保存失败」。

**改法**：捕获 `PGRST204`（列不存在），剔除 `expo_id` 后重试，本地房间同步置空。→ 用户可随时执行迁移，不会因此打断功能。
