# 同窗会 · 双人配对设计讨论（2026-10-03）

> 状态：**讨论中，未拍板**。多人间方案本轮不受影响。
> 前置：硬伤修复 6 项已完成（见 `同窗会硬伤修复_2026-10-03.md`）。

## 起点

用户认可「双人间 = 房主从申请人中挑人」（前一轮选项 1），
随即自己发现该模型的漏洞，并提出改为参考微信最早的「摇一摇」。

## 用户指出的漏洞

> 「如果所有人都是发起人，那申请人存在于哪里？」

**诊断成立，且比表面更严重。**

用数字看：10 个人同时想找人——
- **房主模型**：10 人各自建双人间 → **10 个只有 1 人的房间**，全员等待，无人申请
- **摇一摇**：10 人同时举手 → **5 对**，无需任何人先当房主

关键：这不是概率问题而是**结构问题**。「发起同窗会」是首页主 CTA，
UI 把所有人推向同一个角色（房主）→ 冷启动时自我锁死。

**代码佐证**（本轮实测）：
- `RadarRoomView.addSelfAsParticipant()`：进房间就是把自己 push 进数组，**零门槛、零确认**
- 所以「双人间」若只加容量上限，实际是「**容量 2，先到先得**」——第二个进来的人是随机的，那不是配对，是抢座位
- 现有 `zhonggu_requests` 有完整 `pending → accepted/declined` + `acceptRequest` 生成 `conversation_id` 的骨架，可直接复用为「同意」动作

## 两模型对比

| | 房主 + 申请 | 摇一摇（双向举手） |
|---|---|---|
| 角色 | 不对称（房主 / 申请人） | **对称**（都是举手者） |
| 谁先动 | 房主先建，然后等 | 双方同时 |
| 冷启动 | N 房主 → N 空房 ❌ | N 人摇 → N/2 配对 ✅ |
| 挑选权 | 房主挑 | 无（靠筛选条件） |
| 同意 | 房主单方同意 | **双方各自举手 = 双向同意** |
| 筛选/安全 | 有（房主看过申请人才同意）✅ | **无** ⚠️ |
| 残留 | 空房间可能滞留 | 信号过期即消失 ✅ |

## 判断

**摇一摇方向成立**，因为它解决的是「角色不对称」——
「谁先动」这个问题在房主模型里需要回答且答案是随机的，摇一摇里不用回答。

**且意外契合用户自己定下的三条**：
1. 意图是**临时项** → 摇一摇天然是「我**现在**有空」，而非「我长期想找 coser」
2. **删除是好的** → 信号过期即消失，不留空房、不留尸体
3. 漫展场景 → 人就在现场，「现在」是真实的

**资产复用**：刚做的 `expo_id` + 意图优先权重**正好是摇一摇的筛选器**。
故不应是「摇到随机陌生人」，而是「摇到**同一场漫展 + 意图互补 + 时段重叠**的人」。无需重做。

## ⚠️ 撞底线的地方

摇一摇**取消了筛选**。房主挑人模型里「房主看过申请人才同意」是安全网；
摇一摇是**双方举手即配对，谁都没看过对方**。

微信摇一摇最终死于这个：陌生人随机配对 → 骚扰 → 被边缘化。
**它不是不好用，是没有门槛。**

用户底线：**安全**。

**建议：要它的机制，不要它的赤裸。**
> 摇到 → 先看对方卡片摘要（兴趣/意图，无头像 —— 符合 L0 默认）→ 双方都点「想认识」→ 才开房

同意仍双向（摇），筛选也保留（卡片）。
且线下同场同时段本身就是真实世界的门——**双方确实在同一地点**，强于纯线上随机配对。

## 待用户拍板

**摇到之后：直接开聊，还是先看卡片再决定？**
- 直接开聊：最快最"摇一摇"，但陌生人零筛选进入
- 先看卡片：多一步，但可在看到对方是谁之前决定要不要 ← **建议此项**

（多人间不受影响，仍是「谁都能进」的聚集地。）

## 用户第二轮提案（20:35）——**配对 ≠ 对话**

> 「配对并不是对话，而是一些基本信息进行交换（并非全部公开，
> 可以设置可公开信息和不可公开信息），如果不认可，就放弃此次配对进行下一次？」

### 判断：比「先看卡片」更清楚，补上了摇一摇缺的那块

上一轮的建议「摇到 → 先看卡片再决定」只是模糊的感觉；
用户此案把动作**定义清楚了**，且把同意门放对了位置：

> **骚扰发生在对话里，不在配对里。**

拆开配对与对话 = 在危险发生**之前**插一道门；
而摇一摇原本是「摇到即开聊」，门开在危险**之后**。

### 关键发现：这条路已有半成品

`MatchDetailView.vue` 现已有 L0/L1/L2 阶梯（shareLevel 0/1/2）：

| 层 | 现有实现 |
|---|---|
| L0 模糊摘要 | 只见「维度」（otherFuzzyTags），不见具体内容 |
| L1 已分享卡片 | 交换人设卡 |
| L2 联系方式 | 互授权 |

所以用户说的「可公开/不可公开」≈ 这条已存在的阶梯。
**不需新造，而是把 L0/L1/L2 从「详情页里的一个控件」提升为「配对流程本身」。**

### 用户提案的第二个优点（模型补充）

「放弃此次配对进行下一次」的意义不在机制，在**心理成本**：
- 拒绍一个好友申请 = 有社交成本（面对一个具体的人）
- 跳过一次配对 = 无成本
- 对女性用户关键：拒绍可见可能招致报复，**静默跳过更安全**

→ 建议：被跳过的一方**不知情**（否则反复被拒会积累怨气）

### ⚠️ 待定坑：可公开/不可公开 若是「全局设置」会有反效果

若用户在设置里勾选哪些公开：
1. 全设私有 → 配对时什么都看不到 → 匹配率暴跌且用户不知原因
2. 于是所有人解锁一切 ← **保护自我失效**
3. 恶意用户可「全部接受」批量收集

**更稳的做法**：每层揭示什么是**产品定的**，愿不愿意往下走是**每次配对决定**的。
即「梯子内容固定，走不走按次决定」。

### 三段式（模型建议）

```
摇（我准备好了） → 配对（看到你是谁，接受/跳过） → 开房（真正开始聊）
```

每一步的同意都比上一步更具体。

**但这意味着「双人间」从第二段变成第三段** ——
房间不再是配对的地方，而是配对**成功之后**的地方。

### 待用户拍板（两项，定完则设计闭合）

1. 可公开信息 = **全局配置**，还是**产品固定分层 + 每次配对决定走不走**？
2. 配对成功 = **终点**（交换完即结束，不留痕迹），还是**通向聊天的一道门**？

模型倾向：① 按次决定；② 通向聊天的一道门（即配对成功需再双方同意一次才开房）。

## 用户拍板（2026-10-03 20:42）

### ① 分层方式：**产品固定分层 + 每次配对决定走不走** ✅

> 「产品固定分层 + 每次配对决定走不走我认为这是有效果的」

**为什么这个选择关键**（模型补充）：它使保护成为**默认态**——
不设不等于设为公开，而是**不设就等于有保护**。
避开了「隐私市场化」陷阱（每个人最优 = 别人开放我保守 → 要么没人匹配，要么全解锁）。

### ② 被跳过方**无感 / 不可见** ✅

> 「被跳过（筛选）的一方是无感的也是重要的，最好让被跳过“不可见”，
> 当然可能匹配时间会变长，确实在体感上可能是被跳过了许多次，
> 但作为一种保护机制还是有效果的」

**用户已主动承担代价**（匹配时长变长 / 体感上可能反复被跳），
判断保护价值优先 —— 与三条底线中的「安全」一致。

### ⚠️ 模型发现的新风险：小池子里可能**永远零匹配**

左滑式不可见过滤能成立的前提是**池子够大**（约会 app 百万级）。
但 P0 场景是**一场漫展 ≈ 几十人**：双向不可见过滤 × 小池子 → 可能**一次都匹配不上，且双方都不知道为何**。

**调优旋钮 = L0 模糊摘要的「模糊度」**：
- 太糊（只写“同好”）→ 谁都跳过 → 零匹配
- 太露（写具体作品）→ 安全受影响

### 缓解建议：展示**池子规模**（聚合值，不涉个人）

等待时显示「这一场有 8 个人在找」（**不显示是谁**）：
- 「没人」与「我被跳过了」可区分 → 等待变得**可行动**（可自行调意图/放宽）
- 聚合值不泄露个体，不破坏“被跳过不可见”
- 把「黑等」变成「可自我修正的等」

### 实现细节（模型建议）

- **跳过 = 不写任何记录**（默认行为，反而更省代码）
- 需**本地** skip list（不落库，只有跳过方知道）
- 防重复：「本次不再出现」应对**双方对称**——否则“怎么老是他”会反向泄露「你在被跳」
- NG 过滤是**另一套**：绝对屏蔽、已实现，不属于 skip

## 用户第三轮提问（20:45）——「配对成功之后算什么」

> 「我认可你的双重确认，但是如果我们配对成功，之后做什么，
> 如果不开房，我们会进行下一次配对吗？那这次的成功算什么」

### 诊断：模型上一轮的提案有**真实漏洞**

漏洞不在双重确认，而在：**模型给配对加了一个「后续」，于是它悬空了。**
「配对成功 → 再确认 → 开房」产生了一个状态：**成功了，但还没发生任何事。**
这是产品里最难受的状态——用户做了动作，系统给了肯定，然后没有下文。

### 解开：配对不应有「后续」，它本身就是完整的

**配对成功 = 一次已完成的信息交换（用户自己的定义：「不是对话，是基本信息交换」）**

- 产物 = 卡片可见（你知道对方是谁 / 兴趣 / 意图）
- 类似漫展上换了张名片 —— 换完这件事就结束了，没有「之后」

所以三个问题的答案：

| 用户问题 | 答案 |
|---|---|
| 之后做什么？ | 什么都不用做，它已完成 |
| 不开房会进行下一次吗？ | 会，而且不冲突 |
| 这次成功算什么？ | 算「认识了这个人」，产物是卡片 |

**「开房」不是配对的延续，是新事** —— 从「认识」到「说话」需重新主动发起。
不开房不算失败：没得到对话，但知道了在场有这个人。

### 双重确认因此变得合理

两道门问的是**不同的事**，才不重复：

| 第一道 | 第二道 |
|---|---|
| 我愿意让这个人看到我 | 我愿意现在开始说话 |
| 关于**这个人** | 关于**此刻** |
| 交换信息 | 投入时间 |

若两道门问同一件事（「你愿不愿意和这个人交流」），第二次就是废话。

### 配对成功**不排他**（关键判断）

排他会把产品推成**约会软件（一对一）**，而用户做的是「同好连接」。
- 排他：对方不理你 → 你被**占住**，还找不了别人 → 正是「不开房算失败」那种焦虑的来源
- 不排他：你可以同时认识几个人 —— **这就是漫展扩列**

不排他不会变成公共目录，因为两个天然限流：**时间窗** + **同时在场同时在找**。

### 与用户既往判断的呼应

> 「漫展扩列常变成列表「尸体」，不需要这种关系」

所以配对成功应当是**轻的** —— 它的价值是「你曾经有过选择」，而不是产生一段要维护的关系。

### 待定：卡片留哪里、留多久

- **A. 只在本次同窗会有效** —— 时间窗一过即消失（最符合「删除是好的」）← **模型建议**
- B. 留在「我的」—— 可能又变回「尸体列表」
- C. 不落列表但保留识别 —— **实为已被用户砍掉的「见过的同好」tag**，不采用
