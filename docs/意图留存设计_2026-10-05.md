# 意图留存设计（同窗会「我想要 / 我能提供」）2026-10-05

## 用户决策
- 交互：**A 方案**（textarea → chips 选择器）
- 留存数量：**5 个**
- 两栏数量**相同**（我想要 5 / 我能提供 5）

## 一、问题现状（摸查结果）

「我想要 / 我能提供」出现在**两个入口**，两处都是**纯 textarea 手打**（逗号/顿号/换行分隔，`parseTags()` 解析）：

| 入口 | 文件 | 位置 |
|---|---|---|
| 发起同窗会 | `src/views/RadarLaunchView.vue` | L13-14 定义、L221-236 两个 textarea |
| 推窗配对 | `src/views/PairView.vue` | L41-42 定义、L341-352 两个 textarea |

而人设卡的「我的意图」页（`IntentView.vue`）**已有 chip 词库**：
- `wantMeetPresets` 11 项 / `wantDoPresets` 10 项 / `providePresets` 11 项
- 仍有「自定义输入 + 已选列表 + × 删除」完整交互

即：**词库已存在，但同窗会这两个框还在让人从零手打**——这是本条路上最大的摩擦点。

## 二、设计原则

### 1. 「想要」与「提供」性质不同
| | 我想要 | 我能提供 |
|---|---|---|
| 属性 | 短期需求、场景性强 | 长期能力、稳定 |
| 变化频率 | 每次可能不同 | 数月不变 |
| 留存价值 | 中 | 高 |

→ 结论：两者**分离存储**（独立 key），但**采用同一套排序与数量策略**（用户已定：数量相同）。

### 2. 排序：衰减分数（最近使用 × 使用频次）
**不采用纯 recency**（会把常用项挤掉），**不采用纯 frequency**（会僵化）。采用指数衰减：

```
score = count × 2^(−daysSinceLastUse / 14)
```

- 半衰期 14 天：两周不用，权重减半
- 既反映「最近在用」的惯性，也保留「长期常用」的地位
- 一周内用过 3 次 → score ≈ 3×0.76 = 2.28（靠前）
- 半年前用过 5 次 → score ≈ 5×0.0001 ≈ 0（自然淘汰）
- **不使用全站热度**：会让所有人趋同（永远「同担」第一），失去个人化

### 3. 数量：5 个
- 手机竖屏 chip 约 60–80px 宽，5 个 = 一行多一点，**扫一眼即完**
- 长尾分布下前 5 个覆盖约 70% 的重复选择；第 6 个起边际收益断崖
- 5 个是「浏览」而非「查找」的心理量级
- **历史区与预设区必须分开**：历史 5 个 + 预设全量混排会变成 15+ 个 chips，就不叫快捷了

### 4. 存储：本地（localStorage），不落云端
- **隐私**：意图可能暴露敏感信息（想找同担=暴露口味，想找人陪=暴露孤独）。P0 阶段 RLS 为放开状态，落云端等于任何登录者可读
- **顺带收益**：断网可用（与 v0.9.23.4 网络化方向一致）
- 代价：换设备丢失 —— P0 可接受
- 归一化：trim + 去首尾标点 + 拉丁字母小写后比较去重（`约稿 ` 与 `约稿` 合并）

### 5. 两条底线
- ⚠️ **只展示，不自动预填**：自动填入上次意图会让用户忘改就发出——发出的是他没意识到在说的话。**准确性优先于方便**
- ⚠️ **记录时机 = 成功发起之后**：打了又改、填了又放弃的不进历史。**真用出去的才算数**

### 6. 清除入口
隐私要求可撤回：历史行支持**长按单个删除**；行尾提供「清空」清除该栏全部历史。

## 三、实现方案

### 新增 `src/lib/intentHistory.ts`
- 存储 key：`kizuna.intentHistory.want` / `kizuna.intentHistory.provide`
- 结构：`{ text, count, lastUsedAt }[]`
- API：
  - `getHistory(kind): HistoryEntry[]` —— 按衰减分数降序
  - `getTopHistory(kind, n=5): string[]` —— 取前 N 的文案
  - `recordUsage(kind, tags: string[])` —— 成功发起时调用；累加 count、刷 lastUsedAt
  - `removeHistoryItem(kind, text)` —— 单条删除
  - `clearHistory(kind)` —— 清空该栏
- 上限保护：内部最多保留 50 条，防止无限增长

### 新增 `src/components/IntentPicker.vue`（两入口共用）
一个组件解决「两个入口共享同一份历史」的一致性要求：
- 已选区：chip + × 删除
- **历史区**（≤5，有历史才显示）：标签「最近用过」+ 长按删除 + 行尾「清空」
- **预设区**：折叠在「更多选择」后；**历史为空时默认展开**（冷启动兜底）
- 自定义输入：常驻，回车/＋ 添加
- `v-model` 绑定选中数组

### 修改 `src/views/RadarLaunchView.vue`
- 两个 textarea → `<IntentPicker>`（我想要 / 我能提供）
- `intentWant/intentProvide` 由 `string` 改为 `string[]`（与 PairView 语义统一）
- `parseTags()` 不再需要（保留给别处用则不动）
- 提交成功后调 `recordUsage('want'|'provide', ...)`

### 修改 `src/views/PairView.vue`
- 同上替换
- `openSignal()` 成功后记录
- `openRoomWith()` 传 query（已存在，无需改）

### ⚠️ 顺带修复：query 传了但没人读（同型 bug）
`PairView.openRoomWith()`（L272-274）跳转时传了：
```js
query: { intentWant: ..., intentProvide: ... }
```
注释写「房间的 intent 由本次配对信号带入，**避免重复填写**」。
但 **`RadarLaunchView.vue` 从未 `useRoute` / 读取 `route.query`**（已 grep 确认）。

→ 即：**这句话从没成立过**，配对后开房仍需重新手打一遍。
与「在场确认最高 50 分」「你们看见了彼此」属同一类**「UI 宣称未做之事」**。

修法：`RadarLaunchView` 加 `onMounted` 读取 `route.query.intentWant/intentProvide` 预填。
（注：此处预填合法——是用户刚刚亲手输入的意图的顺延，非历史自动填入）
