### 已发现的事实性问题（非设计选择，是缺陷）

1. **`onlineCount` 硬编码 `ref(1)`**，全项目只在 `RadarRoomView.vue` L23 声明、L336 显示、L265 参与解散判断——**从未被赋值或订阅**。
   - 连带后果：L265 `otherCount = onlineCount - 1` **恒为 0** → 解散确认弹窗（"房间还有其他 N 名用户，确认解散同窗会吗？"）**永不触发**，永远走"直接解散"分支。这个 v0.9.23.3 专门做的弹窗实际是死代码。
   - 且房间顶部"N 人在线"展示的是假数据。

2. **UI 文案在说谎**：`ExpoDetailView.vue` L220 对用户承诺「在场确认后，同窗会会优先匹配同时段在场的人（最高 50 分）」。
   - 实测：`searchRadarRooms` 里**没有任何在场/时段逻辑**，房间也不挂漫展。承诺不成立。

3. **`setTimeout` 做延迟删除不可靠**：`radarStore.ts` 房主退出用 `setTimeout(..., 60_000)` 物理删除。用户切后台/杀进程时定时器不执行 → 房间与消息**永久残留**（正好违背 Q1 隐私修复的初衷）。

4. **`participants` 脏数据**：参与者退出（`closeRadarRoom` 非 initiator 分支）只打 log，**不从 participants 移除**；`addSelfAsParticipant` 失败也不回滚。数组只增不减。

5. **房间不绑漫展** → "同场/同时段"这条最强匹配维度（PRD 里 Scene 权重 30/100）对同窗会**完全没生效**。

6. **排序悖论**（2026-08-12 Q2 已识别，未修）：`isMine ? 100` → 房主进首页看到自己房间霸榜第一。

7. **匹配对象错位**：房间已存 `intent_want[]` / `intent_provide[]`，但排序用的是"发起人 vs 我"的**兴趣**匹配（interest 45%），房间自己的意图字段**没参与排序**。

8. **死代码**：`RadarView.vue` (17.3 KB) 与 `RadarRoomsView.vue` (7.7 KB) —— 路由 L20-21 已注释，全项目 grep **无任何 import 引用**。
   - 注：2026-08-26 PRD 曾判"RadarView 仍被 import"，现已失效（当时 HomeView 尚引用）。

9. **明文密码**：`password?: string | null  // 明文存（P0 演示用）` —— 存 Supabase，任何能读 `radar_rooms` 的人可读。

## 二、待决问题（提请理念对齐）

### 理念层（决定重构方向）

**Q1 同窗会到底是什么？**
名字（同窗=同学）与实现（陌生人临时房间）有语义落差。三个候选：
- A 招募贴：房主发"想找XX"，别人应征 → 现实现
- B 群聊房间：多人在临时空间交流，像现场的"同好碰头点"
- C 配对后开房：系统先配对，两人再进私聊

**Q2 要不要绑定漫展？**
- A 绑定（只能从漫展详情页发起，自动带场地 + 时段）
- B 不绑（泛用临时房间工具）
- C 两者并存

**Q3 匹配的是什么？**人 vs 人的兴趣，还是房间意图 vs 我的意图？（后者才是"你要什么/我能给什么"）

**Q4 「遇见」之后呢？**房间解散 = 关系归零。是否做转化（成为新朋友 / 保留"见过的同好"）？
